## Git 版本控制：你的金钟罩、铁布衫

对于 AI 辅助编程，**版本控制**的重要性怎么强调都不为过。可惜的是，很多非专业程序员常常忽视这一点。如果你曾希望设计稿能一键回到某个历史版本，或者曾不小心删掉过重要内容，那你应该能体会到版本控制的价值。在[第 3 课](zh/Lesson_3_Workflow.md)中，我们简单接触了 Git 的基本操作，这里会做更深入的讲解。

Git 就像是你项目的高级存档系统，远比简单的“保存”要强大得多。你可以把它想象成在不同时间点为你的工作创建“快照”。你可以随时在这些快照之间穿梭、比较差异，甚至将不同版本的功能合并到一起。

为什么说与 AI 协作时，Git 变得尤为重要呢？

**AI 会犯错。** 它有时会搞砸你原本正常的代码，有时会完全跑偏。有了 Git，你就可以大胆地让 AI 去实验，因为你总能轻松回滚到上一个正常工作的状态。

**AI 迭代飞快。** 在一次编程会话中，你可能会经历几十次迭代。Git 能帮你清晰地记录下哪些尝试是成功的，哪些是失败的。

**AI 助你协作。** 无论是与真人协作，还是同时与多个 AI 对话，Git 都能让整合不同来源的代码变得安全又简单。

### Git 的几个核心概念

你无需成为 Git 大师，但理解以下几个基本概念，将使你的 AI 辅助编程效率大增：

- **仓库 (Repository / repo):** 你的项目文件夹的“超级版”，它能追踪所有文件的每一次变更。
- **提交 (Commit):** 项目在某个特定时间点的快照。把它想象成游戏里的“存档点”。
- **分支 (Branch):** 一条独立的时间线。你可以在分支上随心所欲地实验，而不会影响主代码。

尽管许多现代 AI 工具（如 Cursor）内置了类似“检查点”的版本控制功能，但它们有时并不可靠。因此，使用 Git 能为你提供一层额外的安全保障。好消息是，你不需要事必躬亲，只需为 AI 添加以下规则，让它代劳即可：

```
在引入更改或创建新功能时，请确保使用 git。首先检查 git status，然后在必要时创建功能分支。

编写简洁且描述性的 commit message，例如：`类型: 描述`。对于类型，使用祈使动词，如 edit/fix/refactor。对于简单的更改，使用单行 commit message；对于复杂的更改，使用详细的描述。
```

## 让效率倍增的工作流秘诀

接下来，我们聊聊那些能区分专业开发者和新手的实战工作流与习惯。这些不只是纸上谈兵的最佳实践，而是能帮你节省大量时间的宝贵经验。

### 频繁保存与提交（与 AI 协作时尤其如此）

这可能是你需要养成的最重要的一个习惯，没有之一。当你和 AI 一起快速迭代时，情况很容易失控。也许 AI 误解了你的意图，重写了一半的可用代码；也许它引入了一个让你抓狂的 bug。

只要你频繁提交，你就永远离“一切正常”的状态只有几分钟之遥。我个人的习惯是，每完成一个有效的改动（哪怕只是个小优化），就立刻提交。

**高手秘诀：** 写好 commit message，未来的你会感谢现在的自己。别再用“修复了 bug”这样模糊的描述，试试“为登录表单添加用户认证功能”或“修复移动端响应式布局错位问题”。

### 使用分支，大胆实验

这就是 Git 分支大显身手的时候了。假设你的应用目前运行良好，但你想尝试一种全新的 UI 设计。此时，你完全没必要在主代码上冒险，而是可以创建一个新分支：

```bash
git checkout -b experimental-ui-redesign
```

现在，你就拥有了一个绝对安全的“沙盒”环境。让 AI 在里面尽情发挥，尝试各种激进的改动和疯狂的想法。如果新设计效果拔群，你可以轻松地将它合并回主分支。如果搞砸了，也无关紧要，只需删掉这个分支，一切复原：

```bash
git checkout main
git branch -D experimental-ui-redesign
```

这样一来，既不会破坏主分支，也无需浪费时间撤销修改，一举两得。

### 小步快跑，增量测试

这一点与我们之前的提示工程课程一脉相承，但值得再次强调：小步快跑，增量修改，这才是与 AI 协作的王道。不要直接向 AI 下达“重构整个用户界面”这样的宏大指令，而是尝试“更新导航栏，加入用户头像和下拉菜单”这样更具体、更微小的任务。

为什么？因为当问题出现时（它总会不期而至），你才能准确定位到是哪一处改动引发的。调试一个微小改动，可比排查整个系统的 bug 简单多了。

### 学会读一点代码

你不需要成为编程专家，但培养基本的代码阅读能力，将让你与 AI 的协作如虎添翼。你不必亲自写代码，但如果你能看懂 AI 的产出，发现明显的问题，你就能：

- 提出更精准的追问
- 在问题萌芽时就将其扼杀
- 在 AI 没能正确理解时，给出更具体的反馈

从最简单的开始：你能否识别出哪部分代码负责处理用户交互？能否找到数据是从哪里获取或保存的？哪怕只是具备基础的模式识别能力，也能让你事半功倍。

如果你觉得读代码实在头大，不妨让 AI 画图来帮你理解。比如，你可以说：“用 Mermaid 图表展示这些组件的协作关系”或“画出这个 API 调用的序列图，包括用户、前端和后端”。

### 使用 Linter 保证代码质量

这是一个许多新手会忽略的专业技巧：使用“Linter”工具来自动检查代码质量。Linter（如用于 JavaScript 的 ESLint 或用于代码格式化的 Prettier）就像是你代码的“语法老师”。

它们能发现常见错误、统一代码风格，甚至识别潜在的性能问题。最棒的是，只要你提出要求，AI 就能生成符合 Linter 规则的代码。你只需在提示或 AI 规则中加入“运行 lint 并修复 lint 错误”即可。

### “先质疑，再验证”原则

这可能是所有思维转变中最重要的一条。对于 AI 生成的代码，我们应该始终秉持“先质疑，再验证”的原则。无论 AI 的语气多么自信，代码看起来多么漂亮，都必须经过严格测试，才能认为它“已完成”。

这不是被害妄想，而是专业精神的体现。你需要测试“愉快路径”（一切顺利的情况），测试边缘情况（输入为空怎么办？），还要测试异常情况（如果 API 挂了会怎样？）。

### 在隔离目录中快速验证

这是我本人探索新想法时屡试不爽的技巧：与其在主项目里冒险，不如另建一个文件夹，让 AI 在那里生成一个隔离的、小型的原型来测试想法。

例如，当我想测试一个新的支付接口时，我会创建一个 `payment-test` 文件夹，让 AI 先在那里构建一个最简原型。一旦验证可行，我再小心翼翼地将它集成到主项目中。

这个方法在测试第三方 API、新框架或复杂算法时尤其有用。

### 高级技巧：多目录并行开发

对于复杂的项目，这里有一个更高级的技巧：在本地维护多个项目的副本（克隆）。这能让你同时运行不同的 AI 对话或实验，而它们之间互不干扰。这也是 [Anthropic 工程团队](https://www.anthropic.com/engineering/claude-code-best-practices) 所采用的方法。

例如，你可以这样组织：
- `project-main/` - 稳定、可用的主版本
- `project-feature-A/` - 开发用户认证功能
- `project-feature-B/` - 实验新的 UI 设计

每个文件夹都是项目的完整副本，你可以在其中任何一个里面安全地进行独立的实验。

## 基础项目组织结构

良好的代码组织能让你和 AI 助手的协作效率更高。这不仅关乎专业形象，更直接影响到项目的可理解性、可调试性和可维护性。

### 模块化的文件结构

用符合逻辑的方式来组织你的文件。别把所有东西都塞进一个文件夹，尝试建立一个能反映应用工作模式的结构：

```
my-project/
├── src/
│   ├── components/     # 可复用的 UI 组件
│   ├── pages/         # 不同的页面/屏幕
│   ├── utils/         # 工具函数
│   └── api/          # API 集成代码
├── tests/            # 测试文件
├── docs/             # 项目文档
└── assets/           # 图片、图标等静态资源
```

这种模块化的结构在与 AI 协作时优势巨大：

- **精准的上下文：** 你可以针对特定文件夹提问（例如，“只更新 components 文件夹”）。
- **调试更轻松：** 当问题出现时，你能更快地定位到问题所在的范围。
- **协作更高效：** 对于低耦合的模块，甚至可以让多个 AI Agent 并行工作。[参考](https://lucumr.pocoo.org/2025/6/12/agentic-coding/)

### 归置好你的可复用组件

还记得第 8 课里我们创建的可复用组件吗？把它们分门别类地整理好，并配上说明文档。创建一个你和 AI 都能轻松查阅的组件库：

```
components/
├── ui/
│   ├── Button.jsx
│   ├── Input.jsx
│   └── Modal.jsx
├── forms/
│   ├── LoginForm.jsx
│   └── ContactForm.jsx
└── README.md  # 组件说明文档
```

## “老虎机”开发模式

让我们聊一种颇具争议、但值得了解的开发哲学。一些拥有无限 AI 使用权限的团队会采用这种模式。[参考 1](https://monadical.com/posts/vibe-code-how-to-stay-in-control.html) [参考 2](https://www-cdn.anthropic.com/58284b19e702b49db9302d5b6f135ad8871e7658.pdf)

传统开发模式是：AI 生成代码 → 你调试修复 → 你优化改进 → 代码可用后提交。

而“老虎机”模式是：AI 生成代码 → 你测试 → 如果失败，就回滚，让 AI 再试一次 → 不断重复，直到成功 → 提交可用的版本。

### 适用场景

这种模式在以下情况可能行之有效：
- **无限的 AI 调用次数：** 你可以无限制地让 AI 重新生成代码。
- **清晰的需求：** 你对“可用”的标准有明确的定义。
- **自动化的测试：** 你能快速验证生成的代码是否符合预期。
- **定义良好的模块：** AI 的工作范围是独立的、有清晰接口的模块。

### 不适用场景

这种模式在以下情况会碰壁：
- 你没有明确的成功标准。
- 你在开发一个牵一发而动全身的复杂系统。
- 你希望在过程中学习和理解代码。
- 你的 AI 调用次数有限。

### 重要提醒

“老虎机”模式只有一个前提：你对“成功”有水晶般清晰的定义，并且最好有自动化测试来保驾护航。否则，如果你无法自动验证 AI 的输出，你最终得到的将是表面光鲜、实则问题百出的“豆腐渣工程”。

## 融会贯通

这些专业技巧并非各自为战，当它们被整合进一个连贯的工作流时，才能发挥最大威力。一个成熟的 AI 辅助开发流程大致如下：

1. **从干净的 Git 状态开始** - 提交所有未保存的改动。
2. **为新功能创建实验性分支**，大胆尝试。
3. **利用清晰的项目结构**，为 AI 提供精准的上下文。
4. **进行小步快跑式的增量修改**，并频繁测试。
5. **每当一个功能可用时，就频繁提交**。
6. **秉持“先质疑，再验证”的原则** - 对所有代码进行彻底测试。
7. **当实验失败时，果断回滚**，毫不畏惧。

这套流程看起来可能有些繁琐，但一旦养成习惯，它将为你节省大量的时间和精力，让你不再为各种问题焦头烂额。你将花更少的时间调试，更多的时间创造。

## 思维之变

也许，最重要的“专业技巧”是一种思维模式的转变。当你养成这些专业习惯后，你会发现，AI 辅助编程不再是“听天由命”，而是创造一个能让你和 AI 都发挥出最佳水平的协作环境。

你将成为项目的架构师和总监，通过建立体系和流程，来引导 AI 更高效地工作。你不再是随机提问、祈祷好运，而是在精心设计一个高效的开发流程，而 AI 在其中扮演一个能力强大、但需要被引导的合作者角色。

这正是“跟着感觉走”的 vibe coding 与专业的 AI 辅助开发之间的天壤之别。两者各有其用武之地，但掌握专业的方法，将赋予你挑战更宏大、更复杂项目的信心。

请记住：我们的目标不是完全消灭 AI 的错误，也不是一次就写出完美的代码。我们的目标是创建一个让错误可控、进展可追、成功可复制的工作流程。

你一定能行。现在，去创造一些了不起的东西吧。
