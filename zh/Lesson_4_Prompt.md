## 与 AI 对话的艺术

你可能不信：**给 AI 写 Prompt，本质上是在搞管理。** 想想看，管理团队成员时，你不会只甩下一句“把网站做得更好”。你会提供完整的背景信息，设定明确的预期，划定好范围，并引导他们一步步实现你想要的目标。

（我真的认为这节课教的技巧，不仅适用于与 AI 对话，在日常工作协作中也同样有效。工作中那种没头没尾的需求，我见得太多了。）

同样的原则也适用于 AI 编程工具。区别在哪？你的 AI “员工”能力超群，但也格外“死板”。它只会严格按照你的指令行事。如果你的指令含糊不清或缺少关键背景，那你得到的结果可能在技术上满足了要求，但实际上南辕北辙，完全不是你想要的。

掌握了这门艺术，你会发现自己开发起来事半功倍，烦恼也更少。

## 怎样才算一个好的 Prompt？

一个出色的 Prompt 和一个平庸的 Prompt 到底差了什么？关键在于以下几个要素，它们能将模糊的请求，转化为精确的指令：

### 清晰与具体：准确传达你的意图

**糟糕的 Prompt**：“给用户做个表单。”

**优秀的 Prompt**：“创建一个联系表单，需要包含姓名、邮箱和消息三个输入框，以及一个提交按钮。表单需要有客户端校验功能：1. 所有字段都是必填项；2. 实时高亮错误；3. 在所有字段校验通过前，禁用提交按钮。请使用语义化 HTML、无障碍 ARIA 标签，并基于 Vue3 和 Tailwind CSS 实现。”

区别显而易见：优秀的 Prompt 没给 AI 留下任何需要猜测的空间。AI 明确知道要包含哪些字段、添加什么校验、最终做成什么样。

### 提供背景，明确优先级

这正是第三课中提到的工作流大显身手的时候。还记得我们讨论过的 `requirements.md`、`system_design.md` 和 `todo_list.md` 这几个文件吗？它们是你提供丰富上下文，同时又避免让 AI 信息过载的秘密武器。

你不再需要每次都重复输入，只需引用这些文档即可：“请根据 `requirements.md` 中的需求，实现 `system_design.md` 中描述的用户认证流程。”

提供背景也意味着要明确优先级。如果你在构建原型，就直接说。如果性能至关重要，就强调它。如果需要优先适配移动端，就最先提出来。

随着 AI 模型的能力越来越强，我甚至认为“Prompt 工程”这个词或许应该改成“上下文工程”。因为你具体怎么遣词造句变得次要，而你在 Prompt 中提供了哪些上下文信息，则变得至关重要。

### 划定边界：明确约束条件

AI 工具的创造力有时会“泛滥成灾”。我注意到，在那些更强的推理模型上尤其如此，它们总想“自作主张”，做出一些超出你要求范围的优化或重构。

如果没有约束，你可能只是想要一个简单的按钮，结果却得到一个带有动画、状态管理和一堆你根本不想要的依赖的复杂组件。

当你想让 AI 做一个范围明确的修改时，一定要清楚地告诉它限制条件：
- “只修改注册表单里的按钮组件，别碰其他任何东西。”
- “使用 `src/components/` 目录中已有的 Vue 组件，不要添加新组件。”
- “只修复和注册表单相关的功能。暂时不要去优化冗余代码、模块化或性能。”

### 期望的输出：具体说明你想要什么

你想要的到底是什么？是对策略的分析，还是一份实施计划，或者只是一段代码？请明确说出来。

- “请提供包含内联 CSS 的完整 HTML 文件”
- “只给我 JavaScript 函数，并为关键步骤添加注释”
- “给我一个分步实施计划，先别写代码”

## 在对话中迭代与管理上下文

记住，**这是一场对话，而非一次性指令。** 不要指望在第一个 Prompt 里就做到尽善尽美。相反，把它看作是一次你来我往的协作。

### 小步快跑，及时纠偏

还记得我们的工作流吗？不要一上来就说“给我写全部代码”。最好先从确认方案入手：

“我想做一个待办事项应用。根据我的 `requirements.md`，你认为最好的组件结构是什么？”

让 AI 先提出一个方案。如果方向不对，立刻纠正：“实际上，我想让它更简单点。我们能不用 React，只用原生 JavaScript 吗？”

这样可以避免 AI 洋洋洒洒给你写出 200 行你根本不想要的框架代码。

### 追问的力量

有了基础之后，就可以在此之上迭代构建：
- “现在给邮箱输入框加上验证。”
- “把提交按钮改成蓝色，并添加一个悬停效果。”
- “增加 API 调用失败时的错误处理。”

你的每个新请求都建立在之前的对话之上，功能也一步步变得更完善。别忘了随时用 Git 提交你的代码，记录下每一步的变化。

### 知道何时该“另起炉灶”

有时候，对话会完全跑偏。AI 可能卡在某个错误的假设上，或者因为你同时处理多个功能，上下文变得一团糟。这种情况被称为**上下文污染（Context Pollution）**——即早期的误解会污染后续的每一次沟通。

当这种情况发生时，别犹豫，果断开启一段新对话。如有必要，先回滚代码再重新开始。这通常比在一个已经混乱的对话里反复纠缠、调试要快得多。

### 向 Cloudflare 工程团队学习

Cloudflare 的工程团队发现了一个极其高效的沟通模式：**“你这里做的是 X，但实际上应该是 Y，请修改。”**

不需要长篇大论，也没有复杂的指令。只用一句话点明现状、修改原因和正确方向。这种方式就像给同事提反馈一样——直接、有上下文、可落地。

## 4.3. 高级 Prompt 技巧

一旦掌握了基础，这些高级技巧将让你的 Prompt 水平更上一层楼：

### 少样本提示（Few-Shot Prompting）：不只是说，更要“演”

与其费力描述你想要什么，不如直接给它看几个例子：

“这是我项目中其他卡片的样式：@card_example.vue。请遵循相同的设计模式和 CSS 结构，创建一个新的推荐卡片。”

大多数 AI 编程工具都允许你直接引用现有文件。请大胆使用这个功能——这就像是给了你的 AI 一份现成的风格指南。

### 寻求替代方案

不要满足于第一个解决方案。AI 工具可以生成多种实现方式：

“给我展示两种实现这个下拉菜单的方法——一种用纯 CSS，另一种用 Tailwind CSS。”

对于小规模的实验，可以借助临时文件。而对于更重大的架构决策，你甚至可以要求 AI 创建不同的 Git 分支来分别测试。

### 三思而后行：先规划，后行动

前面我们提到了行动前规划的重要性，并谈到要为项目准备系统设计文档和待办事项列表。

这一点同样适用于局部修改。在要求 AI 写代码之前，先让它给个计划。

“在写代码之前，先列出需要创建或修改的文件，以及实现的先后顺序。”

这会给你一张清晰的路线图，帮助你在“一头扎进代码”之前，提前发现潜在的问题。

### 将 Prompt 视为代码文档

这是一个高手技巧：把你最关键的 Prompt 写进 Git 的提交信息或项目文档里。不是全部对话，而是那些引导了重要架构决策或复杂功能实现的关键 Prompt。

未来的你（或你的队友）在试图理解某段代码为什么这么写时，会感激不尽的。这就像是为未来的调试和维护留下了“面包屑”线索。

（Cloudflare 的工程团队在用 Claude 生成他们的 [OAuth 2.1 库](https://github.com/cloudflare/workers-oauth-provider)时，就是这么做的。）

### 一图胜千言

如果你的 AI 工具支持，千万别低估图像的力量。无论是设计稿截图、有问题的 UI 界面，甚至是手绘的线框图，都可以发给 AI。在以下场景中，图片能提供非常有效的上下文信息：
- **设计实现**：“实现这个界面” [附上设计稿]
- **Bug 报告**：“在移动端，布局会像这样错位” [附上截图]
- **架构图**：“实现这个数据库结构” [附上图表]

## 融会贯通

当你将所有这些技巧融会贯通时，你就能和 AI 合作得游刃有余。从清晰的需求文档入手，使用具体且有约束的 Prompt，在对话中迭代，及时纠偏，并在必要时果断另起炉灶。

在下一课中，我们会深入一些技术细节，帮助你更好地理解你正在构建的东西。如果你是编程和应用架构方面的新手，这会是一份绝佳的入门指南。
