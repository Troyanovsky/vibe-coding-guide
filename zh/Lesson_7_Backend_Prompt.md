## 后端：应用的“引擎中枢”

后端开发有这么一个特点——它不追求光鲜亮丽的用户界面，而是专注于那些让应用得以运转的底层逻辑、数据处理和系统性能。打个比方，如果说前端是餐厅里设计精美的用餐区，为顾客提供直观体验，那么后端就是这家餐厅的厨房、库房以及所有维持其正常运作的后台系统。

当你为后端开发向 AI 编写 Prompt 时，你其实是在向一位经验丰富的工程师交付设计蓝图。但关键在于，如果你的蓝图模糊不清，AI 给出的代码或许能勉强运行，但很可能存在安全隐患、效率低下，或者难以维护。因此，你的 Prompt 必须清晰地说明“如何做”：数据如何组织、逻辑如何处理、系统各部分之间如何通信。

这就像你对厨师说“随便做点好吃的”，还是给他一份详尽的菜谱，上面写明了食材、烹饪步骤和摆盘要求。显然，后者才能保证你每次都能得到稳定、可靠的美味佳肴。

## 好的后端 Prompt vs. 差的后端 Prompt

我们来看一个具体例子，让你更直观地理解我的意思。假设你希望用户能在你的应用里保存自己的菜谱。

### 糟糕的 Prompt 示例：
```
“我希望用户能保存菜谱。”
```

**为什么这个 Prompt 很糟糕：** 这个指令实在太模糊了，AI 不得不做出大量假设。比如：
- 该用什么数据库？
- 用什么编程语言和框架？
- “菜谱”具体包含哪些信息？
- 用户通过什么 API 端点来“保存”？
- 如何识别用户身份？需要身份验证吗？
- 数据需要校验吗？

这无异于让厨师“做道菜”，却不告诉他食材、菜系、口味偏好，甚至用餐人数。AI 只能凭空猜测，最终结果很可能与你的实际需求相去甚远。

### 优秀的 Prompt 示例：
```
“请使用 Node.js 和 Express 框架，创建一个 REST API，允许已登录用户保存和获取他们的个人菜谱。数据存储在 PostgreSQL 数据库中。关于 `recipes` 表的具体结构、`POST /api/v1/recipes` 和 `GET /api/v1/recipes` 这两个端点的详细要求（包括请求体、响应格式、身份验证、数据校验规则等），全部定义在 `@system_design.md` 文件里。”
```

**这个 Prompt 为何高效：** 这个 Prompt 简洁而信息量巨大，提供了清晰、可执行的指令。它明确了：
- **技术栈** (Node.js, Express, PostgreSQL)
- **核心功能** (保存和获取菜谱)
- **身份验证**要求
- 最关键的是，它引导 AI 去查阅 `system_design.md` 文件，以获取所有具体的技术细节。

这样一来，AI 就完全清楚要构建什么，以及在哪里找到详细规范，无需任何猜测。

## 优秀后端 Prompt 的几大支柱

每一个优秀的后端 Prompt 都应该覆盖以下五个核心领域。你可以把它们看作是 AI 工程师构建一个稳固系统所必需的设计蓝图。

### 1. 技术选型 (Foundation)

这部分关乎你的技术栈——也就是构成你后端服务的基石。

**需要明确的内容：**
- **语言/运行时:** Node.js, Python, Go, Rust, 还是其他？
- **框架:** Express, Django, Flask, Gin, Actix Web, 还是其他？
- **数据库:** PostgreSQL (关系型), MongoDB (文档型), Redis (内存型), 还是组合使用？

**为什么重要：** 技术栈决定了 AI 生成代码的一切——从语法、可用的库，到与数据库的交互方式。指定“使用 Node.js、Express 和 PostgreSQL”与“使用 Python、Django 和 MongoDB”，给 AI 的工具箱是完全不同的。

### 2. 数据模型 (Data Model)

这部分定义了数据如何组织和存储，是整个应用的根基。

**需要明确的内容：**
- **Schema 定义:** 你的数据表或集合有哪些？ (例如 `recipes`, `users`, `user_recipes`)
- **字段与类型:** 每个表有哪些字段，它们的数据类型是什么？ (`title` 是 `TEXT`, `ingredients` 是 `JSONB`, `user_id` 是 `UUID`)
- **关系与约束:** 表之间如何关联？(例如 `users` 到 `recipes` 的一对多关系)。字段是否需要 `UNIQUE` (唯一)、`NOT NULL` (非空)，或者设置外键约束？

**为什么重要：** 一个定义良好的数据模型，如同为房屋打下坚实的地基。如果数据结构混乱或不一致，整个应用都会变得不稳定且难以预测。

### 3. API 设计 (API Design)

这部分定义了外部系统（如你的前端）如何与后端进行交互。

**需要明确的内容：**
- **端点 (Endpoints):** URL 路径是什么？ (例如 `/api/v1/recipes`, `/api/v1/recipes/:id`)
- **HTTP 方法:** 支持哪些操作？ (GET 获取, POST 创建, PUT 更新, DELETE 删除)
- **请求/响应格式:** 请求和响应的 JSON 结构是怎样的？明确请求体和头部的格式。
- **状态码:** 明确成功的状态码 (200, 201, 204) 和常见的错误码 (400, 404, 500)。

**为什么重要：** API 是后端与客户端（无论是 Web 前端、移动 App 还是第三方服务）之间的“合同”。如果这份合同模糊不清，沟通问题就会接踵而至。

### 4. 业务逻辑 (Business Logic)

这是应用的“大脑”，是那些让你的应用与众不同的特定规则和流程。

**需要明确的内容：**
- **核心流程:** 每个端点具体做什么？ (例如，“保存菜谱时，自动将其与当前登录用户的 ID 关联起来”)
- **数据校验:** 对输入数据有什么规则？ (例如，“菜谱的 `title` 和 `instructions` 不能为空”，"`ingredients` 必须是一个非空数组”)
- **身份验证与授权:** 谁能做什么？ (例如，“只有登录用户才能保存菜谱”，“用户只能查看和删除自己的菜谱”)。如何验证身份？(JWT, API Key, 还是 Session？)

**为什么重要：** 业务逻辑将一个普通的数据库系统，转变为一个能解决实际问题的、有价值的服务。没有清晰的业务逻辑，AI 只能构建出一个“能用但没用”的空壳。

### 5. 安全与性能 (Security & Performance)

这部分关乎如何保护你的应用，并确保它在真实场景下依然表现出色。

**需要明确的内容：**
- **安全措施:** 如何保护数据？ (例如，“使用参数化查询防止 SQL 注入”，“对所有用户输入进行验证和净化”，“使用 bcrypt 对密码进行哈希处理”)
- **错误处理:** 出现问题时怎么办？ (为字段缺失、数据无效、权限不足等情况定义清晰的错误信息；实现全面的日志记录)
- **性能考量:** 有无特定的性能要求？ (例如，“为 `recipes` 表的 `user_id` 字段创建索引，以提高查询效率”)

**Vibe Coders 的常见误区：** 这里有个非常关键的点——许多“凭感觉编程”的初学者容易忽略安全问题，比如不小心将私有的 API 密钥上传到公开的代码仓库，或者忘记实现 API 的速率限制 (rate limiting)，这会带来意想不到的账单和安全风险。如果你想避免这些问题，**必须**在 Prompt 中明确要求 AI 使用环境变量来管理敏感凭证，并为公开的 API 端点添加速率限制。

**为什么重要：** 一个不安全或响应缓慢的后端，无论其业务逻辑多么优雅，都是一个失败品。安全和性能不是“附加项”，而是“必需品”。

## 从何处着手：善用你的系统设计蓝图

如果你是后端开发或“Vibe Coding”的新手，可能会觉得上述概念有些难以消化：数据建模、API 设计、安全考量……这么多细节，到底该从哪里开始定义呢？

**这时，你的 `system_design.md` 文件将是你的得力助手！** 还记得课程前面我们让 AI 帮忙创建的那份项目架构文档吗？它就是你构建一切的蓝图。

你的 `system_design.md` 文件应该包含了以下关键信息：
- 你选择的**技术选型** (技术栈及其决策原因)
- 你的**数据模型** (数据库表结构、关系、约束)
- **API 设计** (端点规范、请求/响应格式)
- 关于**业务逻辑**的初步构想 (核心流程、校验规则)
- **安全**考量 (身份验证方式、数据保护策略)

**千万不要跳过规划阶段。** 在没有清晰设计的情况下直接编写后端 Prompt，就像在没有图纸的情况下建造一台复杂的机器。你很快就会迷失方向，最终要么构建出一个不完整、不一致的系统，要么留下一个充满安全漏洞的烂摊子。

在开始编写后端 Prompt 之前，请回到你的 `system_design.md` 文件，为上述五大支柱的每一项提取必要信息。这能确保整个应用的一致性，并为你的 Prompt 提供坚实的基础。

## 后端 Prompt 的专业技巧

以下是一些久经考验的技巧，能让你的后端 Prompt 更加高效：

**安全与成本控制：** 除了 API 密钥，务必让 AI 为**所有**敏感信息使用环境变量，包括数据库连接字符串、JWT 密钥、第三方服务密钥等。同时，明确要求对公开的 API 端点设置速率限制，以防滥用和意外的高额账单。相信我，你绝对不想一觉醒来，发现因为 API 被恶意调用而收到一张 500 美元的云服务账单。

**统一的错误响应格式：** 要求 AI 在所有端点上实现标准化的 JSON 错误响应，例如 `{ "status": "error", "message": "输入无效", "code": 400 }`。这不仅让前端调试更简单（当出现问题时，你可以直接把这个错误信息丢给 AI 帮你分析），也为 API 的使用者提供了可预期的体验。

**善用日志，你的“黑匣子”：** 始终要求 AI 为关键操作、错误和请求添加基础的日志记录。当生产环境出问题时（这是迟早的事），完善的日志往往是决定你能在几分钟内解决问题，还是需要花上数小时进行“侦探工作”的关键。

**模块化的代码结构：** 要求 AI 将代码组织成逻辑清晰的模块或目录，例如 `routes/`, `controllers/`, `models/`, `middleware/`, `services/`。这能极大地提升代码的可读性和可维护性。同时，这也让你未来的 Prompt 更高效，因为你可以让 AI 只修改特定模块，而不影响整个代码库。

**数据库迁移 (针对关系型数据库)：** 如果你使用 PostgreSQL 或 MySQL 等关系型数据库，请让 AI 为你创建数据库迁移 (migration) 脚本。这对于以一种受控、可追溯、可回滚的方式管理数据库结构变更至关重要。它就像是为你的数据库结构准备的版本控制系统。

**用 Prompt 生成测试：** 这是使用 AI 的一大优势——它非常擅长生成测试代码。在创建完一个端点后，可以追加一个 Prompt：“现在，使用 Jest 和 Supertest 为刚才的菜谱保存端点编写一套全面的单元测试，需要覆盖成功保存、数据校验失败、身份验证失败以及其他边界情况。” (或者，你也可以采用第 3 课中提到的测试驱动开发模式，从测试入手。)

**保持单一职责原则：** 每次只为一个端点或一小块功能编写 Prompt。这能让 AI 保持专注，生成更清晰、更模块化的代码。每个文件最好只做一件事。相比于处理一大堆相互纠缠的功能，调试和迭代一个定义明确的小模块要容易得多。

**指定第三方库：** 如果你想用特定的库来完成任务，请在 Prompt 中直接点名。例如，“使用 `jsonwebtoken` 处理 JWT”、“使用 `pg` 与 PostgreSQL 交互”、“使用 `express-rate-limit` 实现速率限制”。这可以避免 AI 选择一些你不熟悉或不符合项目需求的替代品。(使用 context7 MCP server 可以为 AI 提供最新的库文档，确保其用法准确无误。)

**使用 REST 客户端进行迭代测试：** 使用 Postman、Insomnia 或 VSCode 插件等工具来测试 AI 生成的 API 端点。这能让你获得即时反馈，帮助你构思出更好的后续 Prompt。没有什么比亲眼看到 HTTP 请求和响应的实际结果，更能让你清楚地了解哪些地方运行正常，哪些地方需要调整了。

## 融会贯通

核心原则是：**在后端开发中，你扮演的是架构师的角色。** 你通过系统设计和具体的 Prompt 提供详细的蓝图，而 AI 则扮演你的专家施工团队，负责技术实现。

你的目标是精确地定义逻辑、数据结构和规则，以便 AI 能够为你的应用构建一个健壮、安全且可扩展的引擎。当你做对这一点时，你不仅会得到一个可靠的后端，更能让它随着应用的需求而不断成长和演进。

请记住——后端对用户来说是无形的，但它是一切功能得以实现的地基。花时间把 Prompt 写好，你就能在未来避免无数次的调试、安全漏洞和性能瓶颈。
