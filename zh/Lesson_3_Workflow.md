## 告别散乱的提问

你可能已经试过用 AI 写代码，甚至做出了几个小玩意儿。这超酷的！但你大概率也和许多人一样，很快就撞了墙：感觉自己提的需求越来越乱，AI 也越来越糊涂，最后项目乱成一锅粥。

问题出在哪？成功的 AI 辅助开发，关键不在于找到那句“神奇咒语”般的提示词，而在于建立一套**结构化的工作流**，让你和 AI 都能目标明确、步调一致。这就像自驾游前规划好路线：你可以说走就走，期待一路惊喜，但有张地图，旅程会顺利得多。

接下来我要分享的这套工作流，不管你是完全不懂代码的产品经理，还是经验丰富的工程师，都能轻松上手。它非常灵活，你可以吸收核心思想，然后根据自己的习惯进行调整。

## 第 1 步：定义与规划

### 写清楚产品需求

在 AI 敲下第一行代码之前，你必须想清楚自己到底要做什么。这听起来是废话，但很多人恰恰跳过了这一步，然后反过来抱怨 AI “不够智能”。

第一步，请详细写下你的**用户故事**和**核心功能**。不要只说“我要做个菜谱 App”，而是要具体到这种程度：

> “作为一个爱下厨的人，我希望能根据家里现有的食材搜索菜谱，这样就不用为了做饭特地跑一趟超市。这个 App 应该允许我输入食材，然后展示出匹配的、图文并茂的菜谱，并且能让我收藏喜欢的菜谱。”

（这只是一个简化版，你能写得越具体越好！）

你给 AI 的需求越明确，后续的沟通成本就越低。

### 和 AI 一起“Vibe-PMing”

如果你和我一样是产品经理，写 PRD（产品需求文档）应该是家常便饭。但如果你没这个经验，也别担心，AI 可以帮你。

当你只有一个模糊的想法时，可以让 AI 帮你**梳理和完善产品需求**。我管这个过程叫 “Vibe-PMing” —— 也就是让 AI 扮演你的产品经理，通过“你来我往”的交流，把一个凭感觉（Vibe）的想法变得清晰具体。

你可以在任何 AI 聊天工具里做这件事，不一定非得是专业的 AI 编程工具。你可以这样开头：“我想做一个能根据食材搜菜谱的 App。帮我梳理一下用户流程和可能遇到的极端情况（edge cases）。记得多问我问题，把需求弄清楚。”

AI 可能会反问你：
- “如果用户搜的食材，数据库里没有怎么办？”
- “用户需要根据饮食禁忌（比如素食、无麸质）筛选菜谱吗？”
- “同一道菜的不同做法或食材替换，要怎么处理？”

多进行几轮这样的对话，随时把新冒出来的想法加进去。让 AI 挑战你的假设，提出你没想到的功能点。当你对产品方向满意后，就让 AI 把所有讨论内容总结成一份清晰的 `requirements.md` 文档，存到你的项目文件夹里。

这份文档，就是你和 AI 在后续开发中的“北极星”。

## 第 2 步：AI 辅助技术设计

### 系统设计与架构

明确了要做*什么*，接下来就要弄清楚*怎么*做。即便你不是技术出身，这一步也至关重要，因为它为 AI 的代码生成工作提供了一个清晰的框架。

让 AI 根据你的需求，推荐一个技术架构。比如：“请根据 `requirements.md` 里的需求，为这个菜谱网站推荐一个基础架构，包括前端结构和可能的后端方案。”

给 AI 的上下文越充分越好：
- 需求文档里的项目概述
- 平台说明（比如是 Web 应用还是手机 App）
- 项目目标和主要使用场景
- 核心功能列表...

如果你的 AI 工具有“架构师模式”之类的角色设定，记得用上。让 AI 生成一份 `system_design.md` 文档，里面要说明整个项目的结构、主要组件以及它们之间的协作方式。

如果工具没有这个模式，你可以试试下面这段提示词，引导它进行结构化思考：

```
请你扮演一名资深软件架构师，按照以下步骤，为我的项目设计方案：

1.  **理解需求：**
    *   深入分析产品需求、用户故事、边缘情况和非功能性需求。
    *   在开始设计前，通过提问与我确认你的理解。
2.  **高阶设计与技术选型：**
    *   设计整体架构，并选择核心技术栈。
    *   解释不同方案的优劣，并给出你的推荐。
3.  **详细设计：**
    *   **组件设计：** 划分功能组件，明确各自的职责（遵循单一职责原则）。
    *   **数据结构设计：** 设计数据模型、数据库表结构和它们之间的关系。
    *   **核心流程设计：** 描绘出关键的用户或数据流程，包括组件间的交互、调用关系和错误处理机制。
4.  **定义规范与工具：**
    *   建议代码风格、Linting 规则和项目目录结构。
    *   规划日志记录方案（如日志级别、格式、存储方式）。
    *   规划测试策略（如单元测试、集成测试、端到端测试）和相应工具。
    *   考虑版本控制和依赖管理方案。
5.  **输出设计文档：**
    *   在项目根目录下创建一个 `/doc` 文件夹，并将以上所有设计内容整理成 Markdown 文档输出。
```

你不需要搞懂每个技术细节，但有了这份“蓝图”，就能避免 AI 在后面写代码时即兴发挥，做出随意的架构决策。

### AI 任务拆解

再大的项目，也是由一个个可管理的小模块组成的（模块化和解耦是软件开发的黄金法则）。你可以让 AI 把系统设计方案拆解成一步步的开发任务。这一招对于 GPT-4o, Claude 3 Opus, Gemini 1.5 Pro 这类强大的模型尤其管用。

把 `requirements.md` 和 `system_design.md` 都作为上下文，然后告诉 AI：“请将这个项目拆解成具体的开发任务，并按照优先级和依赖关系排好序。”

有些 AI 编程工具自带任务管理功能（比如清单或便签），如果没有，就让 AI 生成一个 `todo_list.md` 文件，方便你在开发过程中随时查看。

## 第 3 步：“编码”——迭代式开发

### 参考设计文档进行开发

前期的规划工作，现在终于要派上用场了。你不再需要提“给我做个菜谱 App”这种宽泛又低效的需求，而是可以发出具体、清晰的指令：“请参考 `requirements.md` 和 `system_design.md`，完成 `todo_list.md` 里的任务 #1：搭建好项目的基本 HTML 结构和导航栏。”

**记住，一次只做一件事。** 这点至关重要。别指望用一个提示词就让 AI 搭好整个应用。AI 在处理专注、具体的目标时表现最好。

每完成一个任务，就保存一次进度（强烈推荐用 Git 做版本控制，虽然很多工具也支持自动保存）。这样一来，万一哪里出了问题，你也能轻松回退到上一个正常工作的版本。

### 上下文的力量

在让 AI 生成某个具体组件时，一定要尽可能地引用你之前规划好的文档。这样，AI 才能做出符合你整体设计思路的决策，而不是靠猜。

例如：“请根据 `requirements.md` 中描述的用户流程 1，并参考 `system_design.md` 里的设计，创建一个食材搜索组件。请使用 `recipe_search_component.vue` 的代码作为风格参考。这个组件需要能处理我们之前讨论过的‘找不到对应食材’的边缘情况。”

## 其他常见的 AI 辅助工作流

当然，我分享的只是其中一种与 AI 协作的方式。根据你的具体需求和手头的工具，还有很多其他玩法。下面是一些来自 [Claude Code](https://www.anthropic.com/engineering/claude-code-best-practices) 和其他工具的常见工作流，供你参考：

### 探索、规划、编码、提交 (Explore, Plan, Code, Commit)

这就是我们刚刚详细介绍过的标准循环：定义需求 -> 用 AI 辅助规划 -> 生成代码 -> 提交进度。这个模式简单有效，适用于绝大多数项目。记住，每完成一小步并通过测试后，就及时 `commit`，防止劳动成果白费。万一后面 AI 把事情搞砸了，你还有机会回退到上一个稳定版本。

### 测试驱动开发 (Test-Driven Development, TDD)

如果你对代码的正确性有很高的要求，希望它能精准地按照你的预期运行，那么可以试试 TDD。

具体做法是：先用自然语言清晰地描述一个函数或一个模块应该有的行为、输入和输出，然后让 AI 根据你的描述生成测试用例。等测试用例有了，再让 AI 写出能通过这些测试的代码。

在开发过程中，AI 可以反复运行这些测试，来定位问题并自动修复。这种方法能帮你尽早发现 Bug，确保代码功能符合预期。

### 可视化迭代 (Visual Iteration)

对于注重 UI 的项目，你可以给 AI 提供大量的“视觉素材”作为参考，比如线框图、UI 设计稿，甚至是别的应用的截图。这样，AI 生成的代码在视觉上就能更贴近你的想法。

在开发时，你可以先生成代码，预览一下视觉效果，然后根据看到的结果，用更具体的语言或截图来调整你的下一个提示。截图是非常强大的上下文，比如：“整体布局不错，但这个按钮把下面的文字挡住了，能帮我把它往上移一点吗？”

### 安全地“YOLO” (Safe YOLO / 实验分支)

有时候，你可能会想尝试一个全新的方案，但又怕把现有能跑通的代码改崩。这时，你可以创建一个临时的 Git 分支 (`git checkout -b experimental-feature`)，然后在这个分支上，放飞自我，让 AI 大胆地去生成实验性代码。

如果新方案效果不错，太棒了——把它合并回主分支。如果不行，也没关系，直接删掉这个实验分支 (`git branch -D experimental-feature`)，你的主代码库安然无恙。你甚至可以同时开好几个实验分支，横向对比不同方案的效果，择优录取。

这种方法让你既能自由探索，又能保证主代码库的稳定，两全其美。

## 工作流是你的得力助手

这里的核心思想是：成功的 AI 辅助开发，重点不在于找到什么“神奇咒语”，而在于你和 AI 之间**结构化的协作**。你负责提供方向、上下文和质量把控；AI 负责提供实现速度和技术知识。

这和你与真人开发者合作没什么两样。你不会只是把一个模糊的想法扔过去，然后指望对方能完美实现。你们会先沟通，明确需求，然后一步步协作，最终打造出优秀的产品。

当你遵循这套工作流时，你会发现 AI 变得更“专注”，犯的错误更少，产出的代码也更符合你的预期。更重要的是，你真正理解了自己正在构建的东西，而不是两眼一抹黑，全靠祈祷 AI “做对了”。

## 附录：AI 编程必备的 Git 基础

在前面的内容里，我多次提到用 Git 来保存进度和进行安全实验。如果你是 Git 新手，下面这份极简入门指南应该能帮到你（小提示：你也可以直接问 AI 这些命令怎么用）。

### 核心 Git 命令

**初始化一个新项目：**
```bash
git init                    # 初始化一个新的 Git 仓库
git add .                   # 把所有文件加入暂存区，准备提交
git commit -m "Initial commit"  # 提交你的第一个版本快照
```

**完成一个 AI 任务后的基本操作：**
```bash
git add .                   # 暂存你的改动
git commit -m "实现了食材搜索组件"  # 提交并写清楚这次改动的内容
```

**安全地进行实验 (Safe YOLO)：**
```bash
git checkout -b experiment-new-ui  # 创建并切换到一个叫 experiment-new-ui 的实验分支
# ... 在这里让 AI 自由发挥，生成实验性代码 ...
git checkout main           # 切换回主分支
git branch -D experiment-new-ui  # 如果实验不成功，删掉这个分支
```

**代码出问题了怎么办：**
```bash
git status                  # 查看哪些文件被修改了
git log --oneline           # 简洁地查看提交历史
git checkout HEAD~1 -- filename.js  # 把某个文件恢复到上一个版本的状态
git reset --hard HEAD~1    # 强制回退到上一个版本（注意：会丢掉当前所有未提交的改动！）
```

### 为什么 Git 对 AI 编程很重要

- **版本快照**：每当 AI 完成一个任务，提交一次，就相当于创建了一个“存档点”。
- **自由实验**：在分支上大胆尝试各种 AI 生成方案，不用担心弄乱主代码。
- **追踪变更**：可以清楚地看到 AI 在每次迭代中到底改了什么。
- **团队协作**：如果和他人一起开发，Git 能让所有人的代码井井有条。

大多数 AI 编程工具都集成了 Git，但理解这些基本命令能让你在关键时刻掌控全局。不必追求精通 Git 的所有功能，以上这些命令已经能覆盖 AI 辅助开发中 90% 的场景了。
